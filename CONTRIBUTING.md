# Contributing to the B2 Terraform provider

Thanks for helping. Bug reports and feature requests go through the
[issue forms](https://github.com/Backblaze/terraform-provider-b2/issues/new/choose); security reports
never do (see [SECURITY.md](SECURITY.md)). By taking part you agree to the
[Code of Conduct](CODE_OF_CONDUCT.md).

## Setting up

Install Go and Python at the versions in [README.md](README.md#requirements), plus Terraform for the docs
checks and acceptance tests. Then, inside a Python virtual environment:

```shell
make deps
```

## Before you push

Run the local gate. It mirrors the `lint` and `test` jobs in `ci.yml` and the `changelog` workflow
(dependency check, header check, `golangci-lint`, `go vet`, Python `ruff`, unit tests, docs check):

```shell
make ci
```

Acceptance tests create real B2 resources and may cost money. Run the ones your change touches:

```shell
export B2_TEST_APPLICATION_KEY_ID=your_app_key_id
export B2_TEST_APPLICATION_KEY=your_app_key
make testacc TESTARGS='-run TestAccResourceB2Bucket'
```

If you change a schema (an argument, its description, `Computed`, `ForceNew`), regenerate the docs with
`make docs` and commit the result; `make docs-lint` fails otherwise.

### Changelog entries

`CHANGELOG.md` is generated by [changie](https://changie.dev) from small files in `.changes/unreleased/`.
Every PR that changes the provider, its Python bindings, dependencies or CI adds one:

```shell
make changelog-new
```

Pick the kind (`Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security`, `Infrastructure`) and
write one sentence for provider users: name the resource, data source or argument and say what they see.
If users must change their configuration, or existing resources are replaced on the next apply, say so and
what to do. Commit the generated YAML file with your change. Do not edit `CHANGELOG.md` directly;
maintainers rebuild it at release time (see [RELEASE.md](RELEASE.md)).

The `changelog` check fails on a PR that changes anything other than Markdown, tests or repository
metadata without an entry; a maintainer can apply the `-changelog` label when no entry is warranted.

### Working with coding agents

[AGENTS.md](AGENTS.md) is the map for coding agents (and a quick start for people). Larger changes start
with an `intent.md` under [`intent/`](intent/README.md), and reviews follow [REVIEW.md](REVIEW.md).

## Submitting a pull request

Push a branch and open a PR against `master`. Fill in the template: link the issue, paste the tail of
`make ci`, name the tests that pin your change, and say what could change for existing state. A maintainer
reviews it; every review comment gets fixed or answered before merge.
